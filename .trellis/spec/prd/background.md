# Background

cfdoh 的产品背景与目标; requirements 层功能小节的行为从本文推导.

## 背景

大陆线路访问 Cloudflare 边缘的默认地址时好时坏: 同一个 Cloudflare 网站, 不同运营商, 不同时刻的可达性与延迟差异巨大; 明文 SNI 让线路上的中间设备可以按域名干扰连接. edge-smart-doh (refer/) 用 DNS 应答改写缓解这两个问题: 浏览器经它解析域名时, Cloudflare 返回的地址被替换为按运营商线路实测优选的地址, HTTPS 记录里补入 ECH 配置加密 SNI. 该实现是 TypeScript, 部署依赖 Node.js 运行时与 Caddy 反代两层.

访问链路分两段: 浏览器到 DoH 服务器的连接, 与浏览器到各网站的连接. 应答改写只作用于后者的解析; 前者同样受大陆线路影响 — DoH 服务端部署在 Cloudflare 代理之后时, 客户机到它的连接需要把域名钉到线路最优的边缘地址. cfdoh 由两个组件构成:

- 服务端: 用 Go 复刻 edge-smart-doh 的全部行为语义, 收敛为单二进制部署, 在并发, 缓存与防击穿上加强.
- 客户端: 用户机上的常驻服务, 拉取候选地址, 本地测速, 维护 hosts, 把配置的一组 Cloudflare 代理域名 (含 DoH 域名) 钉到当前最优地址.

两者叠加实现全链路优选. 优选地址数据来自众包测速站的公开池 API (默认 cfhub): 服务端定时拉取已发布的运营商池与全国池, 逐池校验后写入池层, 失败沿用旧池, 优选域名池始终作为兑底. 上报端点保留对探针生态的兼容; 客户端可可选把本地测速结论上报给自己的服务端 (默认关闭). 客户端候选源含公开池 API, 优选域名与静态列表, 测速, 滞回与 hosts 维护全部在本机完成.

## 目标

- 行为对齐: 服务端 DNS 应答语义与 edge-smart-doh 逐行为一致, 以其 /explain 输出与测试用例为对照基线; 分歧须在 arch/cdd 层登记.
- 双组件交付: 服务端为单静态二进制; 客户端为常驻服务, 一次安装长期自动运行; 两组件可独立部署.
- 全链路优选: 浏览器经本方案解析后, 到 DoH 服务器与到各 Cloudflare 站点的连接均使用实测优选地址.
- 解析可靠性: 任一上游, 池层, 探针数据失效时逐层回落, 解析不中断, 不返回劣于 SERVFAIL 的结果; 客户端测速全部失败时保留 hosts 现状不动.
- 优选与 ECH 生效: Chromium 系浏览器经本服务解析后, 对 Cloudflare 站点用上优选地址与 ECH.
- 抗污染: 外部上报与公开池写入只能在 Cloudflare 自有网段内影响地址选择, 无法把客户端引向第三方主机; 客户端写入 hosts 的地址必须通过本地测速.
- 隐私: 服务端默认零查询日志, 客户端 IP 只用于选池与构造 ECS 子网, 不落盘; 客户端默认不上报, 开启上报时仅发测速结论.
- 性能: 常见查询 P99 服务端耗时不高于对照基线; 热点查询并发不击穿上游.
- 交付自动化: CI 测试全绿为合并门槛; 打 tag 自动产出双组件多平台二进制与容器镜像, docker compose 一键部署.
