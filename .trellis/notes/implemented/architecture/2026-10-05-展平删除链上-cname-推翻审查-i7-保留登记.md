# Agent Note: 展平删除链上 CNAME-推翻审查 I7 保留登记

Status: implemented
Scope: internal/rewrite/rewrite.go, .trellis/spec/arch/rewrite.md

## Problem

2026-10-05 菜包实测: www.runoob.com (Cloudflare 站 + 上游应答 CNAME 首位形态) 经本服务解析后浏览器报 "找不到服务器 IP 地址"; 关闭 DoH 同站可访问, 确认产物非法. 全仓审查 D 报告 I7 曾登记 "链上 CNAME 记录保留 (refer 删除)" 并判断 "主流应答形态结果等价" — 该判断错误, 但推翻它需要理解为什么当初会错登: 保留 CNAME 在纯 resolver 语义下 "看起来无害", 只有把 RFC 1034 的 CNAME 互斥规则与归名动作放在一起看才能发现非法性. 不留 note 的话, 未来 "改齐 refer 之外还能简化" 类清理可能再次把它改回保留.

## Decision

rewrite.Flatten 的删除判定为并存式: 门控 (首条 qname-owned CNAME) 成立且应答含 qname-owned 非 CNAME 记录 (归名产物与钉住补造产物同样触发) 时, 删除链上全部 CNAME; 无并存 (全 CNAME, 或 CNAME 属其他 owner) 时原样返回. 语义对齐 refer flattenAliases 与 Cloudflare 权威侧 CNAME Flattening. rewrite.md 边界句与 PRD F-012 同步.

## Alternatives considered

- 保留 CNAME 但不归名 (放弃展平) — 输掉: Chromium ECH 可用性判定要求 A/AAAA 与 HTTPS 同 owner, 不展平则 ECH 不生效, F-012 目标丢失.
- 归名但保留 CNAME (审查 I7 原登记) — 输掉: 产出 qname CNAME + qname A 同名并存, RFC 1034 非法, Windows/Chrome 严格解析器拒收, 实测站点不可访问.
- 仅修归名路径不修钉住补造路径 — 输掉: 补造产物同样是非法并存 (check 复核发现), 同族缺陷留一个就是下一个 "某站打不开" 工单.

## Consequences

- 对外应答中 ECH 主机的 CNAME 链消失, 客户端抓包观察不到链 — 与 Cloudflare 官方 CNAME Flattening 行为一致, 无功能损失.
- 合法形态 (非 ECH 主机的 CNAME 链, CNAME 属其他 owner) 不受影响.
- Chromium ECH 判定条件 (单一 owner) 在展平后天然满足.
- 审查登记的边界描述被推翻时, 应核对 "登记的偏差是否本身违反 RFC/协议合法性", 不能只比对自己与 refer 的功能差异 — 这是 I7 漏判的教训.
